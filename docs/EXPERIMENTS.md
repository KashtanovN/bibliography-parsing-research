# Сохранение и фиксация эксперимента

Настройка правил, промпта, форматтера и оценщика выполняется на DEV. TEST используется для итогового сравнения с заранее зафиксированными настройками. Изменение подхода после просмотра TEST требует отдельного эксперимента; программа не может запретить исследователю читать файлы, поэтому это также правило работы с данными.

## Что сохраняется

Каждый запуск получает новую папку, старые файлы не перезаписываются:

- `run.json`: часть DEV/TEST, SHA-256 Excel, число записей, параметры команды, тайм-аут, время начала/окончания и состояние запуска, Java/ОС/архитектура, контрольные суммы фактически загруженных классов и версии POI/Jackson; настройки каждого метода и полученные версии сервисов.
- `rules.jsonl`, `grobid.jsonl`, `ollama.jsonl`: ID, исходная строка, извлечённые поля, полный исходный ответ, предупреждения или ошибка, длительность и время вызова. Запись сбрасывается в файл после каждой ссылки. Сбой сохраняется как ERROR, не заменяется ответом другого метода.
- `summary.json`: число SUCCESS/EMPTY/ERROR каждого метода. Незавершённый новый запуск имеет состояние STARTED и не допускается к оценке.
- `evaluation/records.jsonl`: **каждая** пара «метод — ссылка», включая полностью правильные ответы. В одной записи находятся исходный ответ, ошибка, поля и результат сравнения всех 17 полей: MATCH, BOTH_EMPTY, MISSING, EXTRA, WRONG или EXCLUDED_AMBIGUOUS. Здесь же TP/FP/FN, пригодность записи для полного сравнения и признак полного совпадения. При неоднозначности полный признак равен null.
- `evaluation/comparison_manifest.json`: версия оценивания, реализация оценщика, SHA-256 исходных файлов и полного журнала сравнения.
- Остальные файлы evaluation содержат сводки, precision/recall/F1 и расхождения; formatting и quality связываются по тем же ID. Оформление и подтверждённые добавления требуют решений по протоколу QUALITY_REVIEW.

Для Qwen фиксируются модель, digest весов, параметры квантования, версия Ollama, полный системный промпт и его версия, JSON-схема, seed, temperature, think, num_ctx, num_predict. Для GROBID — ответ `/api/version`, версия адаптера и отключение обогащения Crossref. Для правил — версия и контрольная сумма реализации.

У старых запусков нет новых временных отметок/полного снимка кода. При пересчёте они остаются отсутствующими/null, не восстанавливаются задним числом. Исходные файлы таких прогонов не меняются.

## Зафиксировать протокол после DEV

Из `backend`, после сборки и завершения полного DEV всех четырёх методов:

```sh
java -jar target/bibliography-1.0.0.jar \
  --freeze-experiment=../research-runs/full-dev-20261028 \
  --dataset=../датасет.xlsx
```

Создаётся `frozen-protocol` в папке DEV. В нём `protocol.json`, его контрольная сумма, копии критериев QUALITY_REVIEW/EVALUATION/FORMATTING и, при запуске собранного приложения через `java -jar`, сам `application.jar` с контрольной суммой. Запуск из IDE определяется по байткоду классов; чужой JAR тестового загрузчика не архивируется. Другую новую папку можно указать через `--protocol-output`.

Протокол фиксирует dataset SHA, размеры DEV/TEST, конфигурации четырёх методов, серверные версии и digest модели из DEV, выбранный тайм-аут, нормализацию, форматтер, протокол предметной проверки и текущий байткод программы. Замена JAR на пересобранную/изменённую реализацию может потребовать новой фиксации **до** TEST. Чтобы сохранить возможность воспроизведения, используйте архивированный JAR.

При отсутствии сведений о версиях сервисов протокол не создаётся. Если выбран старый DEV, в котором не сохранялись тайм-аут или байткод, это явно отражено `devTimeoutRecorded: false` / `devImplementationRecorded: false`. Текущий код фиксируется для будущего TEST; архив не объявляется доказательством неизвестного старого байткода. Тайм-аут будущего TEST задаётся при фиксации `--timeout-seconds` (по умолчанию 180).

## Итоговый запуск TEST

```sh
java -jar ../research-runs/full-dev-20261028/frozen-protocol/application.jar \
  --parse-dataset=../датасет.xlsx \
  --method=all --split=test \
  --protocol=../research-runs/full-dev-20261028/frozen-protocol \
  --output=../research-runs/final-test
```

TEST с `--method=all` требует все четыре метода и всю тестовую часть, без `--limit`. До извлечения проверяются dataset SHA, размер TEST, код программы/оценщика, модель/digest, полный промпт, настройки и версии сервисов. Изменение адреса сервера допускается при сохранении тех же версий и конфигураций; адрес записывается в новом run.json. Перед запуском сверяются метаданные серверов; это не утверждение, что сервер невозможно изменить во время обработки — за стабильностью сервисов во время опыта должен следить исследователь.

Протокол с критериями и исполняемым JAR копируется в папку TEST. При последующей оценке проверка повторяется по сохранённым метаданным без обращения к сервисам. Метрики нужно вычислять тем же архивированным JAR:

```sh
java -jar ../research-runs/final-test/protocol/application.jar \
  --evaluate-run=../research-runs/final-test \
  --dataset=../датасет.xlsx
```

Ошибки сервисов остаются ошибками в оценке. Для тестового запуска без протокола или после изменения настроек программа выдаёт причину и не начинает извлечение. Повторный запуск того же протокола технически возможен в новой папке; не выбирать удачный повтор как единственный итог и не менять настройки по результатам TEST.

## Прогресс в терминале

Для просмотра уже работающего TEST из корня проекта:

```sh
bash scripts/watch-test-progress.sh
```

Монитор по умолчанию наблюдает `research-runs/final-test-20261029`, обновляется каждые пять секунд и показывает число завершённых вызовов каждого метода, ERROR/EMPTY, прошедшее время и ориентировочный остаток Qwen. Для другой папки передайте её первым аргументом. Параметр `--once` вторым аргументом выводит один снимок. ETA считается по времени завершённых вызовов, до первого ответа используется ориентир DEV; процент относится к количеству вызовов, а не ко времени.

Монитор только читает файлы. Ctrl+C закрывает его и не останавливает сам TEST. Если основной процесс исчезнет, монитор покажет STOPPED. Технические ERROR не равны ошибкам извлечения полей; последние определяет оценщик после завершения.

`bash scripts/run-final-test.sh` запускает неизменённый архивированный JAR, затем автоматически выполняет evaluate-run, format-run и quality-run. Уже существующий запуск не перезаписывается; автоматически повторять ошибки методов скрипт не будет. Код 3 извлечения с сохранёнными ошибками допускается к оценке, чтобы ошибки не исключались из результата. На macOS скрипт запускает caffeinate на время своей работы; крышку MacBook нужно оставить открытой. Вывод сохраняйте в отдельный журнал, если запускаете процесс в фоне. Состояние и PID находятся рядом с папкой запуска в файлах с суффиксами .pipeline-status, .pipeline.pid, .java.pid и .started.

## Дополнительный AnyStyle

`--method=all` запускает все четыре метода; для проверки только AnyStyle доступен `--method=anystyle`. Установка и отображение полей описаны в [ANYSTYLE.md](ANYSTYLE.md). В архивных JAR значение `all` соответствует набору методов зафиксированного эксперимента; опубликованные замеры повторно не запускаются.
