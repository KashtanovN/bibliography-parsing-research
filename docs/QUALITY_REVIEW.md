# Итоговый расчёт и предметная проверка

Протокол `quality-review-v1` дополняет автоматическую оценку извлечения двумя проверками: правильностью готового оформления и наличием необоснованных реквизитов LLM. Все методы проверяются по одинаковым критериям. Согласие разметчиков 97,16% характеризует эталон и не входит в результаты методов.

Актуальные [решения и рассчитанные показатели TEST](../results/review-20261029/README.md) опубликованы отдельно от исходных пустых бланков архивов.

## Получить общий отчёт

Для нового прогона из `backend`, после `./mvnw package` и окончания прогона четырёх методов:

```sh
java -jar target/bibliography-1.0.0.jar \
  --evaluate-run=../research-runs/ИМЯ_ПРОГОНА --dataset=../датасет.xlsx

java -jar target/bibliography-1.0.0.jar \
  --format-run=../research-runs/ИМЯ_ПРОГОНА --dataset=../датасет.xlsx

java -jar target/bibliography-1.0.0.jar \
  --quality-run=../research-runs/ИМЯ_ПРОГОНА --dataset=../датасет.xlsx
```

Архивные прогоны обрабатывайте их собственным сохранённым JAR: текущая сборка имеет другой снимок реализации. Каждая команда создаёт новую подпапку и не перезаписывает существующую. Если `evaluation` или `formatting` уже есть, соответствующую команду повторять не нужно. Можно задать новые пути через `--evaluation-output`, `--format-output`, `--quality-output`. При нестандартном пути оформления передайте его в `--quality-run` параметром `--formatting`.

В `quality/report.md` находятся сводка извлечения, F1 по полям, состояние проверки оформления и добавлений. В `quality/quality_metrics.json` — машинные результаты, включая precision/recall/F1, группы происхождения ссылок и явные знаменатели. В `quality/review.json` — заполненный исходными данными бланк предметной проверки. Пока решений нет, итоговая нормативная доля и общее число неподтверждённых фактов равны `null`, а не нулю. Нижняя/верхняя границы доли оформления показывают диапазон при незавершённой проверке, а не оценку качества на проверенной подвыборке.

## Проверка оформления

Для каждой записи `kind: "formatting"` с `eligible: true` и без `automaticFailure` сверить:

1. Реквизиты и их роли: автор, заглавие, издание, год, том, выпуск, страницы и другие выводимые сведения должны соответствовать исходной строке; пропуски значимых для оформления сведений считаются ошибками. Совпадение с ошибочным эталоном не оправдывает неправильную ссылку.
2. Профиль и контекст: используется заданный ГОСТ и одна и та же выбранная сетевая версия/дата обращения для всех методов. URL и дата из общего контекста не являются выдумками LLM, даже если их нет в исходной строке. Нельзя незаметно дополнять предсказания данными из эталона или сайта.
3. Требования выбранного краткого профиля из `FORMATTING.md` и соответствующего стандарта: состав областей, авторские сведения, сведения о содержащем документе, роль и пагинация страниц, URL/дата и необходимые примечания. Разрешённый стандартом вариант пунктуации не объявлять ошибкой только из-за отличия от эталонной строки. Для специальных случаев нужны подтверждающие сведения; не угадывать.

Изменять в бланке только три строковых значения:

```json
"decision": "correct",
"evidence": "Реквизиты, общий контекст и требования выбранного краткого профиля сверены; замечаний нет.",
"reviewer": "Имя проверяющего / human / дата"
```

Варианты решения: `correct`, `incorrect`, `unclear`; пустая строка означает «ещё не проверено». В evidence указывать конкретную ошибку или основание решения. Если проверяет ИИ, указывать модель и `AI`, не представлять такую проверку независимой человеческой. Статусы `FORMATTED` и `NEEDS_REVIEW` не заполняют решение автоматически. При `NEEDS_REVIEW` возможны неправильность результата или нехватка сведений для решения — выбрать по фактам.

Знаменатель доли полностью корректных оформлений — все записи метода без исходных неоднозначных полей. Ошибки/пустые ответы метода автоматически входят в него как некорректное оформление; их нельзя одобрить вручную. Записи с неоднозначностью исключаются целиком одинаково для всех методов; их число выводится отдельно. Доля публикуется только после решения всех остальных случаев; `unclear` не исключается ради улучшения результата.

## Проверка добавлений LLM

Бланк содержит **каждое непустое поле ответа LLM**, включая совпавшие с эталоном. Поэтому ошибка самого эталона не скрывает выдумку, а конфликтующее значение не пропадает из проверки. Пропуски не являются добавлениями и уже влияют на recall.

Для `kind: "llm_field"` сравнить `predicted` с `rawCitation`:

- `supported` — значение подтверждается строкой в нужной роли; допустима нормализация пробелов, тире, авторских инициалов, даты и идентификатора без новых сведений.
- `misassigned` — значение есть в строке, но отнесено к неверному полю, например номер выпуска принят за том. Это ошибка извлечения, но не новый придуманный факт.
- `unsupported` — добавлено конкретное сведение, для которого в строке нет основания, например отсутствующий год, издатель, автор, URL, дата обращения или дополнительные инициалы. В evidence назвать добавленный фрагмент и объяснить отсутствие основания. Внешне верный факт также является неподтверждённым добавлением в задаче извлечения из строки.
- `gold_error` — строка подтверждает ответ, а эталон размечен неверно; описать расхождение. Это не необоснованное добавление. Сам эталон этой командой не меняется: его исправление потребует новой версии и повторной оценки всех методов.
- `unclear` — основания недостаточны; пустая строка — проверка не выполнена.

`DOCUMENT_TYPE` и `PAGE_MEANING` являются выводимыми категориями, их правильность проверяется по смыслу. Они учитываются в F1, но их ошибки показываются отдельно от количества новых фактических реквизитов. Неоднозначные пары исключаются из проверки фактов по маске; остальные поля этих записей сохраняются.

В сводке отдельно указаны подтверждённое число неподтверждённых фактических полей, количество записей с ними, знаменатель всех предсказанных оцениваемых фактических полей и число ещё не решённых случаев. Только при полной проверке итоговое число и доля становятся определёнными. Если Ollama не участвовала в прогоне, показатель недоступен.

## Пересчитать после проверки

Сохранить заполненный `review.json`, затем выполнить:

```sh
java -jar target/bibliography-1.0.0.jar \
  --quality-run=../research-runs/ИМЯ_ПРОГОНА \
  --dataset=../датасет.xlsx \
  --review-file=../research-runs/ИМЯ_ПРОГОНА/quality/review.json \
  --quality-output=../research-runs/ИМЯ_ПРОГОНА/quality-reviewed
```

Проверяются контрольные суммы Excel, исходных ответов, оформления и конфигурации, состав записей и неизменность всех исходных данных бланка. Нельзя переставлять строки, удалять записи или менять поля кроме decision/evidence/reviewer. Неверные коды, решения без указания проверяющего/основания, одобрение ошибки сервиса или решение по исключённой записи отклоняются. Расчёт сохраняется в новой папке.

## Переход к TEST

Сначала закончить DEV, изучить ошибки и зафиксировать версии правил, GROBID, модели/промпта, форматтера, нормализации и настоящего протокола. Затем один раз обработать TEST без `--limit`, сохранить исходные ответы, вычислить извлечение, оформить и проверить по тому же протоколу. После просмотра TEST не подстраивать методы под эти примеры; изменения требуют отдельного нового эксперимента. Результаты DEV и показатели согласия разметчиков нельзя выдавать за итоговые результаты TEST.
